# Red-team report: Tamtim end-to-end encryption (2026-11-19)

**Not an audit. This report does not replace an independent external security review.** The encryption (MLS RFC 9420 through the unaudited library `ts-mls` 1.6.4) was built and reviewed by Claude sessions, and this attack session was also done by a Claude session: the same model family shares blind spots. Nothing here lets anyone call the app secure or private. The flag `THIKRA_E2EE` stays **off** in production.

## ملخص قصير للمالك (بالعربية)

هاجمنا التشفير كما يفعل مهاجم حقيقي، على قاعدة بيانات محلية مؤقتة فقط (لا موقع حيّ ولا بيانات حقيقية): خادم خبيث، عضو خبيث في المحادثة، جهاز مسروق، صفحة مصابة، وتسريب معلومات جانبي. كتبنا 41 هجوماً كاختبارات آلية. **اثنا عشر ضعفاً ظهرت وأصلحناها** (أهمها: عضو محذوف كان يواصل استقبال إشعارات المحادثة الحيّة؛ الخادم كان يخزّن أي بايتات على أنها «مشفّر»؛ خادم كاذب كان يستطيع إقناع التطبيق بإرسال نص مقروء إلى محادثة مشفّرة؛ والرسائل المحذوفة كانت تبقى نسخة منها على الجهاز). **ما زال مفتوحاً ولا يمكن إصلاحه عندنا:** عضو خبيث يستطيع تعطيل محادثة (تتوقف تغييرات المفاتيح)، الثقة بأول جهاز يظهر لشخص، خادم يخفي آخر الرسائل أو يتواطأ مع شخص محذوف، ومفاتيح لا تنتهي صلاحيتها. **لم نستطع فحصه هنا:** متصفحات وهواتف حقيقية غير المتصفح المحلي، موقع مهاجم حقيقي على الشبكة، رياضيات مكتبة `ts-mls` نفسها، وقنوات جانبية دقيقة (توقيت، حجم). **لا يزال المطلوب مراجعة أمنية خارجية مستقلة قبل أن يُقال لأحد إن التطبيق مشفّر.**

## What was attacked, and how

All attacks are automated tests that FAIL when the attack succeeds: `server/e2ee-attacks.test.ts` (20 tests) and `web/e2ee-attacks.test.ts` (21 tests). They use the real server, the real engine and the real MLS library, with a throwaway in-memory database and temporary blob/backup folders. A hostile member is a real MLS device that sends bytes the honest app never would. A hostile server is played by tampering with the answers the engine reads (or by writing rows directly). Four attacks that still work are kept as `todo` tests (reported, not failing). Run: `node --import tsx --test server/e2ee-attacks.test.ts web/e2ee-attacks.test.ts`.

Severity: critical = a stranger or the server reads message content; high = breaks a main promise (removal, "the server never carries readable text") or leaks content; medium = leaks metadata, breaks integrity or availability for a chat; low = hardening. "Ours" = a flaw in our code; "ts-mls" = in the library; "design" = inherent to the design or to any untrusted-server messenger (accepted and documented).

## Attacks that worked, and were fixed (failing test first, then fix)

| # | Attack | Severity | Whose | Fix | Test |
|---|---|---|---|---|---|
| 1 | A person removed from a chat (or the family circle) kept their already-open live socket in the chat's room: they kept receiving every later live frame (commit, rekey and message frames; for a **family circle that is the readable text**) until they reconnected | **high** (plain circle), medium (encrypted: ciphertext and metadata) | ours (realtime layer, older than the encryption) | `live.evict` on every removal path, also across nodes through the bus; a person added back is put in the room again | server: "an ex-member keeps asking" |
| 2 | The server stored **any bytes** posted as a "ciphertext", commit or welcome: readable text in the ciphertext column, a message of another chat, an old commit replayed, MLS "authenticated data" (sent in the clear), a message whose claimed epoch differs from the epoch inside it (dodges the removal gate) | medium (high if a client ever sends plain text there) | ours | the server reads the plain MLS header (`core/e2ee.ts describeMessage`) and refuses: not an MLS private message, wrong group (`c<chat>`), wrong epoch, wrong content type (commit vs application), non-empty authenticated data, trailing bytes, a welcome that is not a welcome | server: 5 tests |
| 3 | The key directory stored key packages **without verifying** them (signature, leaf signature, ciphersuite, expiry): a broken or foreign-suite package could sit there and make a chat that claims it fail | low-medium | ours | `checkKeyPackage` before storing | server: 2 tests |
| 4 | A request body of JSON `null` made 8 encryption routes answer 500 | low | ours | `readBody` | server: malformed-bodies test (also checks no secret reaches a response or the log) |
| 5 | **Downgrade:** the screen decides "encrypted or not" from what the server says. A hostile server could say "not encrypted" about an encrypted chat and the app would post readable text (and files, cards, polls) into it | **high** against a hostile server | ours | a device that has ever held keys for, or been told by the directory about, a chat remembers it (`web/src/e2ee/known.ts`); the app's `api()` and the socket sender refuse readable posting to it (`encrypted_chat`); the chat screen treats it as encrypted. **Not fixed:** a chat this device has never seen (see open list) | web: 2 tests |
| 6 | Another member's message could make every receiver's **screen fetch a web address** of the sender's choice (the thumbnail field was shown as an image address): a tracking pixel (IP address and the moment the chat is opened), and a sender-chosen file type (`text/html`, `image/svg+xml`) and unbounded numbers of files, options, waveform points and name lengths | medium | ours | `decodePayload` rebuilds every field: thumbnail must be a small inline `data:image/...`, file type reduced to a safe inline list or `application/octet-stream`, sender name must be a device name, caps on files (10), poll options (12 x 300 characters), waveform (300 finite numbers), names, key and hash shapes | web: 4 tests |
| 7 | A person could count as **several voices in a single-choice poll** (a vote may list many options), and vote for options that do not exist | low | ours | the vote is cut to the options that exist and to one option unless the poll allows several | web: poll test |
| 8 | When the browser could not make its sealing key, the device **silently stored its keys and chats unsealed** on disk | medium | ours | `chooseKv`: memory only for that visit (the app already says "not durable"), never unsealed on disk | web test |
| 9 | After "delete for everyone" the words stayed on both devices: the sent-copy cache (`oc:`), the chat-list preview, edit history, reactions and votes, and the control messages were re-applied at the next read (and so also reached every recovery backup) | medium | ours | purge removes them, remembers the deleted message so control messages about it are dropped, and the sent copy is removed as soon as it is no longer needed | web test |
| 10 | The **8-digit short code** compared between two devices could be matched by grinding an Ed25519 key (about 10^8 tries, minutes on a laptop) | medium (the old "approve by short code" path; the typed/QR link code is the strong path) | ours | 12 digits (about 40 bits; still not a substitute for the link code or the safety number) | web test |
| 11 | The core's parsers accepted **bytes after** an MLS message, so two different byte strings meant one message (a padded copy could use up the real message's key; duplicate checks by hash were bypassed) | low | ours (and the library, which ignores trailing bytes) | `decodeStrict` in the core and on the server | server test |
| 12 | Dependency advisories in `hono` and `@hono/node-server` (middleware skipped for some paths, WebSocket upgrade crash) | medium (not exploitable in our routing as tested: `%0A` and `\` paths still answered 401/404) | third party | updated to patched versions | `pnpm audit` |

## Attacks that were tried and BLOCKED (no change needed)

Forged sender (`from` of another device) shown as unreadable; edit of someone else's message (server 403; header and sealed target must agree); replay of a captured ciphertext (second copy unreadable, later messages still read); reply, edit and mention pointing into another chat or at strangers; prototype pollution through payload, ledger and hand-over keys; a server that lists a different key for a device (the chat is not started with a package whose key differs from the directory); a new unconfirmed device of a known person (not added without a yes); a stranger touching another person's device routes, pairing, hand-over or backup (404); an ex-member on every route and on files; view-once file fetched without "open" or by its sender; a key package of another ciphersuite; recovery phrase (about 124 bits, scrypt N=2^15; damaged or wrong-key backups open nothing); link code and QR (a third key, or both public keys without the shared secret, open nothing; malformed pictures are not links); the sealing key is non-extractable and values are bound to their storage key (moved or tampered values are refused); damaged, truncated and padded bytes in every parser (no hang, honest state unharmed; the server's header reader never throws); plaintext in the database file, a real backup, logs, error answers, live frames and listings (a field allow-list freezes what the server may know); the export; the forward, search, analysis, link-preview, push-text, report, sealed-letter and plain-reaction routes (existing tests, re-checked); `Math.random` is not used anywhere in the key, nonce or file-encryption paths (only reconnect jitter and a fallback call id); cross-site request forgery is blocked by the session cookie being `SameSite=Lax` (there is no Origin check as a second layer: low).

## Still open (honest list, nothing hidden)

| # | Open attack | Severity | Whose | Note |
|---|---|---|---|---|
| O1 | A hostile **member** can post a well-formed commit that removes other members from the keys (they cannot apply it and are stuck) or any commit the others cannot apply; there is no repair route, and after a removal the chat then waits for a commit nobody can make | medium (availability, not secrecy) | design + ours (no repair) | the server cannot read a commit; header checks (fix 2) stop junk and replays, not a valid-looking commit. Needs: a repair action ("start the chat again with a new group") and, better, MLS admin policy |
| O2 | **First-sight trust:** the first device a server lists for a person is trusted; a server can invent a first device (and for a chat a device has never seen, it can claim "not encrypted", see fix 5) | high against a malicious server | design | defence: compare the safety number; the independent review should look at this first |
| O3 | A hostile **server** can hide the newest messages or commits from a device, show different members different histories, or keep delivering old-epoch messages to a removed person who colludes with it; nothing signs the head of a chat | high against a malicious server | design (any server-ordered messenger) | needs a signed head or gossip between members |
| O4 | A co-member can drain a person's one-time key packages (8 per hour per pair); the reusable last-resort package is then handed out again (weaker against replay); key packages never expire (library default lifetime) | low-medium | ours + library default | rate limit is the only mitigation |
| O5 | **View once and disappearing messages** are courtesies between honest apps: the recipient's device holds the file key and text; a modified client can keep them. The server's old ciphertext stays in older backups and in free database pages until they are rewritten | low (accepted) | design | do not describe them as protection |
| O6 | A **stale recovery backup** restored while the old device is still in use can reuse a sender ratchet generation (same key and nonce for two messages: serious for those two messages) | medium | design/ours | the app says "start fresh"; a forced key refresh right after a restore would reduce the window |
| O7 | The authenticated sender leaf is not available from `ts-mls`; the sender check uses the sealed `from` plus the server's user id, so a server colluding with a member can relabel messages in groups of three or more | medium | library | listed since the first review |
| O8 | Metadata the server and a network observer still see: members, times, sizes (256-byte buckets), kind, epoch, mentioned ids, group names and photos, which chats are encrypted, push timing. The server picks which chat a push asks the device to preview, and can show any push text | medium | design (documented) | frozen by the field allow-list test, so it cannot grow unnoticed |
| O9 | Script inside the page (XSS) can ask the browser to use the non-extractable key and read every chat; the sealing protects a copied database file, not a compromised page or an unlocked device | high if it happens | design (stated) | strict CSP exists; not attacked here |
| O10 | A device that never saw a chat takes "encrypted or not" from the server (first sight); a hostile member can still pause a chat by adding unvouched devices (accepted) | medium | design | see O2 and the plan |
| O11 | Two uncovered transitive advisories: `uuid` (moderate) and `fast-xml-parser` (low) | low | third party | not on an encryption path |

The four `todo` tests in the two attack files keep O1 (kick), O4 (drain), O3 (hidden newest messages) and O2 (fake first device) visible in every run.

## What could NOT be tested here

- Real browsers other than the local Node and in-process test setup (IndexedDB behaviour in Safari, Firefox, private windows; storage eviction; real WebCrypto non-extractable behaviour across profiles), and real phones (push, lock screen, camera for the QR).
- A real attacker's position on a real network (traffic analysis, timing, TLS interception, a hostile Wi-Fi), and any live site (forbidden by the brief).
- The mathematics and constant-time behaviour of `ts-mls` and its crypto dependencies (noble curves, `@hpke/core`): no formal proof, no upstream test vectors re-run here, no side-channel measurement.
- Side channels in general (timing of decryption, memory remanence, swap files), and a full dependency audit beyond `pnpm audit`.
- Admin panel and ops agent were checked by reading the code and by the field allow-list (they return counts, not messages), not by an authenticated attack session.

## Conclusion

Twelve weaknesses were found and fixed; more than twenty attacks were blocked; the open list above is the honest remainder, and its first three items need design work, not a patch. The encryption has now been attacked by a second Claude session, which is **not independent**. An independent external review remains required before anyone is told the app is encrypted.

## Independent review of the fixes (2026-11-19)

A separate reviewer read the diff and found 5 real problems in OUR fixes (all fixed, each with a failing test first):
1. Encrypted photos/files/voice could not be sent: the "plain post" guard also blocked the engine's own `/uploads` route (it carries already-encrypted bytes). `/uploads` is no longer guarded; `/attachments` still is.
2. After "delete for everyone", the message's edits/reactions/votes came back as "unreadable" bubbles at every later load. Rows already dropped are now skipped.
3. The chat-list preview could keep the words of a deleted message (the preview now remembers the message id).
4. A removed person's socket closing later could delete the live room of members who joined after the removal.
5. Two browser tabs could erase each other's "this chat is encrypted" marks (the list is re-read and merged before each write).
Also tightened: the key-package upload re-checks the identity key and stock inside the transaction; `catchUp` drops deleted rows.
Still true and not fixed (low): data written in clear by the old fallback is not wiped; a temporary IndexedDB error makes the device look new for one visit (counts toward the 10-device limit); a half-sent message's sent-copy cache can stay on disk until read back.
After these: 639 tests, 635 pass, 0 fail, 4 todo (open attacks). This is still not an independent external audit.
