# Live frames: the WebSocket contract

For whoever builds a client (the mobile app). This is what the server speaks **today**: JSON text frames on one WebSocket. `docs/PROTOCOL.md` is the future binary design, not this. The HTTP side is in `docs/openapi.json`.

Source of truth: `server/ws.ts` and the `publish(...)` calls in `server/lib/`. Tests: `server/ws.test.ts`, `server/presence.test.ts`, `server/network.test.ts`.

## Connecting

- `GET /ws` with the same session cookie as the HTTP API (`thikra_session`). No cookie or an expired one: HTTP 401. A suspended person: 403.
- The server pings every 25 seconds and drops a connection that does not answer.
- On connect the server subscribes the connection to every chat the person is in and sends `hello`.
- Close code `4001` means the session was ended (signed out everywhere, suspended). Do not reconnect with the same session.
- Nothing depends on the socket for correctness. Anything missed is fetched again by `sync` or over HTTP. Reconnect with backoff (the web app uses 0.5 s doubling to 15 s, with jitter).

## Client to server

| Frame | Fields | Meaning |
|---|---|---|
| `ping` | | Answered with `pong`. |
| `visible` | `on: boolean` | The app is on screen (`true`) or went to the background (`false`). Drives "online", "last seen", and whether a push notification is skipped. Send it on connect and on every change. |
| `join` | `circle` | Subscribe to a chat joined after connecting. |
| `send` | `circle`, `client_msg_id` (string, max 64), `body` (max 4000), `reply_to?` (message id), `mentions?` (user ids, max 20), `preview?` (a link that is in the body, see link previews) | Send a text message. Answered with `ack` or `err`. Use one `client_msg_id` per message for every retry: the server stores it once. Limit: 120 new messages a minute; a retry of a stored message is never refused. |
| `read` | `circle`, `seq` | I have read up to this seq. |
| `typing` | `circle`, `on: boolean`, `kind: 'text' \| 'voice'` | I am typing, or recording a voice note. Relayed, not stored. At most 2 a second are relayed. Send one every 2.5 s while it lasts, and `on: false` when it stops. A missing or unknown `kind` is `text`. |
| `sync` | `circle`, and `after_seq` or `after_rev` | Messages after a seq, or new and changed messages after a revision. Up to 200, oldest first. If `more` is true in the answer, ask again. |

| Frame | Fields | Meaning |

| `pong` | | |

"Left" is announced about 4 seconds after the app leaves the screen, and not at all if the person is back before then. `gone: true` means you may no longer see this person (they hid it, or a block): delete what you showed. ## Rules a client must follow

- **Ticks come from marks, not from messages.** Each member has `deliveredSeq` and `readSeq` (in `GET /api/circles/:id`, kept fresh by `receipt`). A message is delivered when every other member's `deliveredSeq` has reached its seq, and read when every other member's `readSeq` has. A member whose `readSeq` is null does not share reads, and the message never shows as read. The rule is in `web/src/ticks.ts`.
- **Read receipts are reciprocal.** If the person turned theirs off, ignore other people's `read_seq`.
- **Presence is decided by the server.** `GET /api/presence?ids=1,2` returns only the people you may see. Someone absent from the answer is hidden: show nothing, not "offline".
- **Presence: also re-ask `GET /api/presence` about once a minute** while a screen shows it. Some changes are not announced (someone left a shared chat, an unblock, your own privacy setting).
- **Sending: one message at a time per chat, oldest first.** Send the next only when the one before is acknowledged. Keep unsent messages on the device, per signed-in person, and wipe them on sign-out. On `rate_limited` or `server` retry after 2, 4, 8, 16 seconds and give up (show "not sent") on the fifth; on no answer keep retrying; on any other error show "not sent". The web's version is `web/src/sender.ts` with its tests.
- **History window:** a screen holds messages from some seq up to the newest. Ignore an `update` for a message older than that window, or scrolling back will skip everything in between (`web/src/history.ts`).
- **Advance your sync position only on `sync` answers**, never on pushed frames. A lost push is then repaired by the next sync.
- **History pages:** `GET /api/circles/:id/messages?before_seq=<oldest seq you hold>&limit=50`. A page shorter than the limit means there is nothing older.
- **Message info:** `GET /api/messages/:id/info`, for the author only.

## Added on 2026-11-19 (groups)

- **Group face:** `description`, `photo` (a media id, fetched with `GET /api/media/:id`) on the chat; `PUT` / `DELETE /api/circles/:id/photo`; `description` and `name` through `PATCH /api/circles/:id`. Who may change them is `editPolicy` (`all` or `admins`).
- **Who may send:** `sendPolicy` (`all` or `admins`) on the chat. A refused post answers 403 `admins_only` on every route, and `err admins_only` on the socket. Show "Only admins can send messages" in place of the message box.
- **Join approval:** `joinApproval` on the chat. `POST /api/circles/join` then answers 202 `{ pending: true }` with no id. Managers: `GET /api/circles/:id/join-requests`, `POST /api/circles/:id/join-requests/:userId { approve: boolean }`, and `joinRequests` (a count) in the chat's details.
- **Mentions:** send `mentions` (user ids) with a text message. A message returns `mentions: [{ id, name }]`; highlight only those. The chat list row has `mentioned` while an unread message mentions you. A mention is pushed even to a muted chat. The web's text rules are in `web/src/mentions.ts`.
- **Polls:** `POST /api/circles/:id/polls { question, options (2–12), multiple?, client_msg_id? }`. A poll is a normal message (its `body` is the question) with `poll: { multiple, closed, voters, options: [{ id, text, voters: [userId] }] }`. Vote with `POST /api/messages/:id/vote { options: [optionId] }`, which REPLACES your votes (empty takes them back). The creator closes with `POST /api/messages/:id/poll/close`. Every vote arrives as an `update` frame and moves the message's `rev`.
- **Notices:** new system notice codes `photoChanged`, `photoRemoved`, `descChanged`, `nameChanged` (`to`), `sendAdmins`, `sendAll`.

## Added on 2026-11-19 (media and sharing)

One envelope: a link preview, a GIF, a sticker, a contact and a location are all an ordinary message with `card` set (`null` otherwise). `card.type` is `link`, `gif`, `sticker`, `contact` or `location`. A client that does not know a type shows the message's text (empty for all but `link`) and nothing else. A quoted reply carries `replyTo.card` (the type only). The chat list's `lastKind` can also be `gif`, `sticker`, `contact`, `location`.

- **Voice notes.** `POST /api/circles/:id/voice` (multipart) takes `client_msg_id`, `waveform` (JSON array of 4-64 numbers 0-100, measured while recording), `duration` (ms) and `reply_to`. Keep the recording on the device until this answers and retry with the SAME `client_msg_id`: it is stored once (201 the first time, 200 after). A message returns `waveform` (or null) and `playedBy` (user ids). When a listener starts playing someone else's note, call `POST /api/messages/:id/played` once; everyone then gets an `update` frame and the message's `rev` moves. Show "played" to the sender when every other member is in `playedBy`. `GET /api/messages/:id/audio` supports `Range` (needed to seek).
- **Resumable uploads.** (1) `POST /api/circles/:id/uploads { name, size }` answers `{ id, offset: 0, chunk }`. (2) `PUT /api/uploads/:id?offset=N` with raw bytes (at most `chunk`) answers `{ offset }`; a piece is taken only if `N` is exactly what the server holds, otherwise 409 `offset_mismatch` with the real `offset`: continue from there. (3) After a dropped connection `GET /api/uploads/:id` answers `{ offset, size }`; 404 `upload_not_found` means start again. (4) `POST /api/circles/:id/attachments` with one `upload` field per file (in order) plus `thumb`, `w`, `h`, `caption`, `reply_to`, `client_msg_id` makes the message. `DELETE /api/uploads/:id` cancels. NOTHING is in the chat before step 4, so a cancel needs no cleanup of messages. Unfinished uploads expire after 24 hours. Limits: 64 MB per file, 16 MB per photo, 10 files; a refusal is 413 `attachment_too_large` with `max` (bytes). The web's version of the rules, with tests, is `web/src/uploads.ts`.
- **Link previews.** While the person writes, the SENDER's device calls `POST /api/link-preview { url }` and gets `{ preview: { url, title, description, site, image } | null }` (`image` is a hash for `GET /api/link-preview/image/:hash`). 400 `unsafe_link` means the address may not be fetched (not http/https, an unusual port, a private or local address). To attach the card, send the text message with `preview: <the same url, as it appears in the body>` (socket `send` frame or HTTP). The message then has `card: { type: 'link', url, title, description, site, image }` where `image` is a media id (`GET /api/media/:id`) or null. The card is built from the server's own fetch; fields sent by a client are ignored. Editing the link out of the text removes the card. Never load a link's page or picture from the device itself.
- **GIFs.** `GET /api/gifs?q=&offset=` answers `{ configured, items: [{ id, title, w, h }] }` (empty `q` = trending). `configured: false` means no provider key is set: say "GIF search is not set up". Thumbnail: `GET /api/gifs/:id/preview`. Send: `POST /api/circles/:id/cards { type: 'gif', id }`. The message has `card: { type: 'gif', provider, title }` and the GIF itself as `attachments[0]` (an ordinary image). Show "Powered by GIPHY" in the search panel.
- **Stickers.** `POST /api/circles/:id/cards { type: 'sticker', pack, id }`; `card: { type: 'sticker', pack, id }`. The packs are in `core/stickers.ts` and are drawn by the app (a greeting badge, or one large emoji); nothing is downloaded.
- **Contact.** `POST /api/circles/:id/cards { type: 'contact', name, phones: [1-5] }`; `card: { type: 'contact', name, phones }`. "Message" is `POST /api/direct { phone }` (404 `user_not_found` = not on Tamtim); "Save" writes a vCard on the device.
- **Location.** `POST /api/circles/:id/cards { type: 'location', lat, lng, accuracy?, label? }`; `card: { type: 'location', lat, lng, accuracy, label }` (6 decimals, accuracy in metres). Open with `https://www.google.com/maps/search/?api=1&query=LAT,LNG` or `https://maps.apple.com/?ll=LAT,LNG&q=LAT,LNG`. No map picture is fetched from a third party.
- **Cards and the rules.** `POST /api/circles/:id/cards` takes `client_msg_id` and `reply_to` like any send, and answers 403 `admins_only` / `blocked`, 423 `circle_frozen`, 400 `invalid_card`, 503 `gifs_off`. A card other than `link` cannot be edited or forwarded.
- **Server setting.** `GIPHY_API_KEY` turns GIF search on. The `Permissions-Policy` header now allows `geolocation=(self)`.

## Added on 2026-11-19 (privacy and extras)

None of these reads message text; each works on ids, timestamps and blobs, so it survives the later end-to-end encryption (design: `docs/superpowers/specs/2026-11-19-privacy-design.md`).

- **Disappearing messages.** `PUT /api/circles/:id/disappearing { seconds }` with 86400, 604800, 7776000 or `null` (off). Private chat: either person; group: owner or admins (403 `forbidden`); family circle: 409 `not_in_circle`. The chat returns `disappearSeconds`. It applies to NEW messages only: each carries `expiresAt` (UTC `YYYY-MM-DD HH:MM:SS`, `null` if none). A notice goes in the chat: `sys` codes `disappearOn` (`name`, `secs`) and `disappearOff` (`name`). When the time comes the server erases the message and its files exactly like "delete for everyone", and the message comes back (by `rev`, and as an `update` or `changed` frame) with `expired: true` and an empty body: DROP it, do not show "deleted". A client should also hide a message locally once `expiresAt` has passed, even offline. The chat list ignores expired messages.
- **View once.** Send a photo or video (`POST /api/circles/:id/attachments`, one file) or a voice note (`POST /api/circles/:id/voice`) with the form field `view_once=1`: no caption, no thumbnail, no transcript. The message has `viewOnce: { openedBy: [user ids] }` (`null` otherwise); its attachments carry no name and no thumbnail. A recipient calls `POST /api/messages/:id/open` ONCE: 200, then `GET /api/media/:id` (or `/audio`) works for 15 minutes with `Cache-Control: no-store`; before it 403 `view_once_closed`, after it 410 `view_once_gone`; a second open answers 410 `already_opened`; the sender gets 403 `view_once_closed` for their own. Opening moves the message's `rev` and sends an `update` frame so the sender sees who opened. When every other member has opened it (and their 15-minute window passed) the file is erased; an unopened one is erased after 14 days (the message stays, with no file). View-once messages are not in the gallery and cannot be starred or forwarded. A web page cannot stop screenshots: say so honestly (see `viewOnceNote`).
- **Chat lock.** `PATCH /api/circles/:id/prefs { locked }` stores ONLY a flag (the PIN or biometrics stay on the device). The chat list and the chat return `locked`. For a locked chat the list returns an empty `lastText`, null `lastMessage`, `lastKind` and `lastAuthor`; a push says only "New message"; the chat's name and members are left out of `GET /api/people`. The device must hide the chat from the main list and ask for its own PIN. Biometrics on mobile belong to the mobile app.
- **Broadcast lists.** `GET/POST /api/broadcast-lists`, `GET/PATCH/DELETE /api/broadcast-lists/:id` (members must be people you share a chat with; 30 lists, 100 people). `POST /api/broadcast-lists/:id/chats` answers `{ chats: [{ userId, circleId }] }`, the private chat of each person (made if needed; anyone who blocked you or whom you blocked is left out). THE DEVICE sends one ordinary message into each chat (`POST /api/circles/:id/messages`, with a client id like `bc-<batch>-<userId>` so a retry is not doubled). Recipients get a normal private message; do not show a count of who received it (it would reveal a block). **When encryption is on:** call it with body `{ "encrypted": true }`: each returned chat (`{ userId, circleId, encrypted }`) is the person's END-TO-END ENCRYPTED private chat, and the device encrypts the message into each one (same `bc-<batch>-<userId>` id) instead of using the plain message route; 409 `e2ee_unavailable` if the server has encryption off. Never fall back to the plain chats when encryption is on.
- **Wallpapers.** `PATCH /api/circles/:id/prefs { wallpaper }`: `none`, `dots`, `dusk`, `dunes`, `forest`, `rose`, a `#rrggbb` colour, or `null` for the person's own default. Returned as `wallpaper` on the list and the chat. Only that person sees it.
- **Voice-to-text.** `GET /api/transcribe` answers `{ configured }` (say "not set up" when false). `POST /api/transcribe` (multipart `audio`, optional `lang`) answers `{ text }`; the DEVICE sends the audio it holds, for ONE note the reader chose; nothing is stored and the message is not changed (keep the text on the device). 503 `transcribe_off`, 400 `invalid_audio` (over 5 MB or not audio), 429 `too_many_requests` (10 a day), 502 `transcribe_failed`. Server setting: `TRANSCRIBE_API_KEY` (an OpenAI-compatible `/v1/audio/transcriptions` service; `TRANSCRIBE_BASE_URL`, `TRANSCRIBE_MODEL` optional). The first use should tell the person the note goes to an outside service.

## Notifications (Web Push), checked on 2026-11-19

Not a socket frame, but the same contract for a client. Payload (unchanged): `{ title, body, circle, tag, url? }`. Code: `server/push.ts`, `server/lib/push.ts`, `web/public/sw.js`, `web/src/push.ts`. Tests: `server/push.test.ts`, `web/push.test.ts`.

- **Who is notified:** every other member with a subscription, except: a muted chat (unless the message mentions them), a person with the app on screen (`visible` frame), a system notice, a suspended or signed-out-everywhere person (their subscriptions are deleted when their sessions end).
- **Text rules:** a person who turned "show text" off, a **locked chat**, a **view-once** message and any message in a chat with **disappearing messages** on all say only "New message" with the title "Tamtim" (no chat name, no sender, not even "photo"). Otherwise: a private chat shows `text`; a group or family circle shows the chat name as title and `Author: text`; media shows 📷 / voice / file words; a card shows its type word. (Family circles keep real text because the server may read them; the end-to-end work will make the other kinds generic.)
- **Subscribe / unsubscribe:** `GET /api/push/key` (VAPID public key, created once and stored), `POST /api/push/subscribe { endpoint (https), keys: { p256dh, auth } }` (the same endpoint under another person MOVES to that person: a shared browser follows whoever signed in last), `DELETE /api/push/subscribe { endpoint }` (own device only), `GET /api/push/status`. The web app deletes its subscription before signing out or deleting the account and re-registers it after signing in.
- **Dead devices:** a 404 or 410 from the push service deletes the subscription; any other error is logged and the device is kept. A failing push service never makes a send fail.
- **Tap:** the service worker focuses an open tab and posts `{ t: 'open', path }` (path like `/#/circle/7`); the page sets its route. With no tab open it opens `path`. Only paths inside the app are used (`url` if it starts with a single `/`, else the chat, else `/`).

## Added on 2026-11-19 (end-to-end encryption, part A)

Design: `docs/superpowers/specs/2026-11-19-encryption-design.md`; choice and plan: `...-encryption-plan.md`. **Off until the server sets `THIKRA_E2EE=1`** (`GET /api/keys/status` answers `{ enabled }`); the app screens (part B) are not built yet. Nothing here changes a family circle or any existing chat.

- **A chat is encrypted or not, from its creation, for good.** `POST /api/circles { kind: 'group', encrypted: true }` and `POST /api/direct { ..., encrypted: true }` (409 `circle_not_encryptable` for a family circle, 409 `e2ee_unavailable` while the switch is off). A pair of people can have a readable direct chat and an encrypted one: different chats. The list and `GET /api/circles/:id` return `encrypted`; the chat also returns `e2eeEpoch`, `e2eeMinEpoch`. No request changes the flag; `POST .../convert` on an encrypted group answers 409 `encrypted_chat`. In the list an encrypted chat has `lastText: ''`, `lastKind: 'encrypted'`, `lastMessage: null` (the device remembers what it last decrypted).
- **Every text-carrying route answers 409 `encrypted_chat` in an encrypted chat:** `POST .../messages` (and the live `send` frame, as an `error` frame with that code), `.../voice`, `.../attachments`, `.../cards`, `.../polls`, `PATCH /api/messages/:mid`, `POST /api/messages/:mid/forward` (from or into one), `GET .../search`, `POST /api/messages/:mid/archive`. Server search does not exist there: search the device's own history.
- **Key directory (`/api/keys`).** `POST /devices { label }` -> `{ deviceId, identity: 'u<user>.d<device>' }` (a device's name inside the protocol; the id comes before its keys). `GET /devices` (mine, with `stock`). `POST /devices/:did/packages { packages: [base64], lastResort?: base64 }`: each must be a valid MLS key package that names this device and carries its one identity key (400 `invalid_package` otherwise); 100 unused packages at most. `DELETE /devices/:did` retires a device (and raises the minimum epoch of all its encrypted chats). `GET /users/:uid` -> `{ devices: [{ id, identityKey, stock }] }` and `POST /users/:uid/claim` -> `{ packages: [{ deviceId, package, lastResort }] }` (one per device; only for a person you share a chat with; 404 otherwise).
- **Commits and welcomes.** `GET /api/circles/:id/e2ee` -> `{ epoch, minEpoch, rekeyNeeded, devices: [{ userId, deviceId, identityKey }] }`. `POST /api/circles/:id/e2ee/commits { device, epoch, commit, welcomes: [{ device, welcome }] }` accepts ONLY epoch = current + 1 (409 `epoch_conflict` with the current `epoch`: fetch, apply, try again); a welcome may go only to a live device of a current member. `GET .../e2ee/commits?after=<epoch>` -> `[{ epoch, userId, device, commit }]`. `GET .../e2ee/welcomes?device=<id>` -> `[{ id, epoch, welcome }]` for that device; `DELETE /api/e2ee/welcomes/:wid` once used. All bytes are base64.
- **An encrypted message.** `POST /api/circles/:id/e2ee/messages { ciphertext, kind, epoch, clientMsgId?, replyTo?, mentions?: [userId], uploads?: [id], viewOnce?, target? }`. `kind` is `text | media | voice | card | edit`; 413 above 64 KB of ciphertext; a retry with the same `clientMsgId` returns the original (200); `mayPost` applies (403 `admins_only`). `epoch` must be at most the group's epoch (409 `epoch_ahead`) and at least `minEpoch` (409 `rekey_required`: wait for the commit). `uploads` are finished resumable uploads of ciphertext (the upload route ignores the file name for an encrypted chat); they are stored as anonymous `file` media. An `edit` names `target` (the sender's own text or media message, within 15 minutes) and wakes nobody. The ciphertext must be an MLS private message of this chat made in the claimed `epoch` (400 `invalid_ciphertext` otherwise; red-team 2026-11-19). A message in `GET .../messages` and in the `msg` frame carries `encKind`, `epoch` and `ciphertext` (base64) and `body: ''`; family circle messages carry none of these keys. Deleting uses the ordinary delete route and erases the ciphertext.
- **New server frame:** `{ t: 'e2ee', circle, kind: 'rekey', reason: 'removed' | 'left' | 'device_revoked', user, minEpoch }` (someone must post the commit that removes them); `{ t: 'e2ee', circle, kind: 'add', user }` (a person joined: a device must add theirs); `{ t: 'e2ee', circle, kind: 'commit', epoch, user }` (apply it).
- **Push** for an encrypted chat is always `Tamtim` / «رسالة جديدة» with the circle id (no sender, no text, no kind); an `edit` sends none.
- **Reports** on an encrypted message take `snapshot` (the text the reporter's device chose to send); the report is stored with `unverified = 1`.
## Added on 2026-11-19 (voice calls, trial)

One-to-one voice calls in a private chat, on the web. The voice goes straight between the two devices (WebRTC); the socket carries only the set-up. Design and limits: `docs/superpowers/specs/2026-11-19-calls-design.md`. Source: `server/lib/calls.ts`; tests `server/calls.test.ts`. Call state is in memory on ONE node.

- **ICE servers.** `GET /api/calls/ice` answers `{ iceServers: [{ urls, username?, credential? }], ttl, turn }`. STUN always (`THIKRA_STUN_URLS`, default `stun:stun.cloudflare.com:3478`); TURN with short-lived credentials (`username = <expiry>:<user id>`, `credential = base64(HMAC-SHA1(secret, username))`, the coturn `use-auth-secret` scheme) only when `THIKRA_TURN_URLS` (comma separated) and `THIKRA_TURN_SECRET` are set; `THIKRA_TURN_TTL` seconds (3600). `turn: false` means no relay: say so when a call cannot connect. 30 a 10 minutes (429).
- **Client to server.** `call_offer {call, circle, sdp}` (`call`: 8-64 chars `A-Za-z0-9_-`, made by the caller; SDP at most 16 KB); `call_answer {call, sdp}`; `call_ice {call, candidate}` (`candidate: null` = end of candidates; at most 80 a side); `call_end {call, reason?}` (the caller cancels a ringing call, the callee's `reason: 'decline'` declines it, after the answer it hangs up; `reason: 'failed'` says the media never connected). Frames for an unknown call, or from someone who is not a party, are ignored.
- **Server to client.** `call_incoming {call, circle, from: {id, name}, sdp, ring_ms}` to every open socket of the callee; `call_answer {call, sdp}` to the caller; `call_ice {call, candidate}` to the other party (the caller's early candidates are held until the answer); `call_taken {call}` to the callee's OTHER sockets once one answers (stop ringing); `call_end {call, reason}` to both sides. `reason`: `cancelled`, `declined`, `timeout` (45 s, `THIKRA_CALL_RING_MS`), `busy`, `offline` (callee has no open page), `ended`, `failed`, `lost` (a party's socket closed mid-call); a refused offer: `not_allowed` (not a private chat or not a member), `blocked`, `frozen`, `maintenance`, `in_call`, `rate_limited` (10 offers per 10 minutes), `bad_request`.
- **The chat record.** An ordinary system notice (`kind: system`, so seq, sync, delete and the chat list work): `callMissed {name}` (the caller), `callDeclined {name}` (the callee), `callEnded {secs}`. A refused call leaves none. Notices never push.
- **Safety code.** Both devices hash the two DTLS fingerprints from the SDPs (sorted) and show 15 digits; the people compare them aloud. `web/src/calls.ts`. Not a substitute for verified identity keys.

## Added on 2026-11-19 (end-to-end encryption, part B: web client)

- A row of an encrypted chat carries `encKind` (`text`, `media`, `poll`, `card`, `voice`, `ctl`, `edit`...), `epoch` and opaque `ciphertext`; `body` is empty. Frames `msg` and `update` carry the same row; the client decrypts at every point a row enters the screen and keeps the plaintext on the device (an MLS key is used once).
- `ctl` rows (reactions, votes) and `edit` rows are control messages: they wake nobody, never count as unread and never show as the chat's last message. A plain `react` call in an encrypted chat is refused with 409 `encrypted_chat`.
- Frame `e2ee` (`circle`) means: new commit or welcome, sync now. Frame `open` makes the device sync every chat.
- Push for an encrypted chat is generic and now carries `enc: 1`; the service worker asks an open page (`{t:'decrypt', circle}` over a MessageChannel, 1.5 s) for the words, otherwise the generic line stays.
- New routes: `GET/PUT/DELETE /api/keys/backup` (opaque recovery blob, 4 MB).

## Added on 2026-11-19 (end-to-end encryption hardening: linking a second device)

- `GET /api/keys/devices` rows now carry `linkProof` (hex, or null). `PUT /api/keys/devices/:did/link { proof }` (64 hex characters; only the device's own person; once: 409 `already_linked`) publishes the proof a new device made from its secret link code.
- The hand-over of history to a new device: `PUT /api/keys/devices/:did/transfer { part, last, data }` (part 0..39, base64, at most 3 MB each, 413 `too_large`), `GET .../transfer` -> `{ parts: [0,1,...], complete }`, `GET .../transfer/:part` -> `{ data }`, `DELETE .../transfer`. Only the person who owns the device; opaque bytes sealed with a key the server never has; removed when the device is retired or takes it. Migration 0026 (`e2ee_devices.link_proof`, `e2ee_transfers`).
- Client only (no frame): a message row an encrypted chat device cannot read yet has `waiting: true` (keys on the way) or `undecryptable` without it (never readable here). New device notices: `new_device_waiting` (kept on the device).

No new live frames for the QR step: linking and safety-number comparison use the existing REST routes (`PUT /api/keys/devices/:id/link` now takes `{proof, pub}`, `PUT .../transfer` part 0 takes `peer`), nothing new is pushed over the socket.


## Added on 2026-11-19 (end-to-end encryption gaps step: a device vouches for another)

No new live frames. REST only: `PUT /api/keys/devices/:did/endorsement { by, sig }` (base64 Ed25519 signature, 64 bytes, made by device `by` of the SAME person over `tamtim-device-v1|u<user>|d<did>|<hex identity key of did>`; 404 when either device is not the caller's, 400 for a bad or non-verifying signature, 409 `e2ee_unavailable` while the switch is off; migration 0027 `e2ee_devices.endorsement`, `endorsed_by`). `GET /api/keys/devices` rows carry `endorsement` and `endorsedBy`; `GET /api/circles/:id/e2ee` devices now carry `endorsement` and `endorserKey` (both null when none). Client only: notice kind `new_device_unconfirmed`; error code `device_unconfirmed` (sending paused) and `device_gone`. Hand-over pieces older than an hour are removed by the server.
