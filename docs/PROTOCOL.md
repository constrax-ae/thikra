# مواصفة بروتوكول ذكرى (المسودة 0.1)

**الحالة:** مسودة للمراجعة. هذه هي الوثيقة التي يُبنى عليها محرك المراسلة (المرحلة 1)، وكل بند فيها يصير اختباراً.
**النطاق:** كيف تنتقل الرسالة والحدث بين الجهاز والخادم وبين الأجهزة. ليست مواصفة التخزين ولا الواجهة.

> **لماذا الآن؟** القياس الأول ([bench/results](../bench/results)) أظهر أن الخادم يكتب الرسالة في 4 ملّي ثانية، لكنها تصل للمستلم بعد **2.9 ثانية (p95)** لأن العميل يسأل كل 3 ثوانٍ، وكلفة الخمول 667 طلباً في الثانية لكل ألف عميل. الخلل في التصميم لا في الخادم، والبروتوكول هو الذي يصحّحه.

---

## 1. المبادئ

1. **الخادم لا يرى المحتوى.** من اليوم الأول تُصمَّم الرسالة بحيث يكون محتواها (`payload`) صندوقاً معتماً للخادم. في المرحلة 1 يكون نصاً صريحاً خلف TLS، وفي المرحلة 2 يصير مشفّراً (MLS) دون تغيير شيء في الظرف. **كل ما يحتاج قراءة المحتوى (البحث، بوابة الذكاء) ينتقل للجهاز.**
2. **الجهاز مصدر الحقيقة للواجهة.** الواجهة تقرأ من قاعدة محلية فقط. الشبكة تحدّث القاعدة في الخلفية.
3. **التسليم مرة واحدة على الأقل، والعرض مرة واحدة بالضبط.** نعيد المحاولة بلا حدود، والمعرّف الفريد يمنع التكرار.
4. **الترتيب بيد الخادم.** لكل محادثة رقم تسلسلي متصل بلا فجوات يعطيه الخادم عند القبول.
5. **صغير وبسيط.** ثنائي ومضغوط، ولا يرسل ما لا يلزم.
6. **كل شيء يمكن أن يفشل.** لكل حالة فشل سلوك محدد (القسم 8).

## 2. المفاهيم والمعرّفات

| المفهوم | المعنى | المعرّف |
|---|---|---|
| **الحساب** (account) | الإنسان صاحب الرقم | `account_id` |
| **الجهاز** (device) | جوال أو حاسوب مسجَّل للحساب | `device_id` (يولّده الجهاز) |
| **الشخص** (person) | فرد من العائلة قد لا يملك حساباً (متوفى، طفل) | `person_id` |
| **المحادثة** (conversation) | مكان تُرسل فيه الرسائل | `conv_id` (UUIDv7) |
| **الرسالة** (message) | وحدة داخل محادثة | الموضع `(conv_id, seq)` |
| **الحدث** (event) | أي إشعار غير مخزَّن دائماً (يكتب، إيصال) | بلا معرّف دائم |

**المحادثة نوع واحد بثلاث صيغ:**

| `kind` | الأعضاء | ما يميّزها |
|---|---|---|
| `direct` | اثنان ثابتان | بلا أدوار |
| `group` | 2 فأكثر | أدوار، دعوات |
| `circle` | كالمجموعة | + وكيل الأرشفة (عضو ظاهر)، وأرشيف، ولحظات |

هذا الدمج هو ما يسمح بتحويل مجموعة عادية إلى دائرة دون نقل شيء.

## 3. ظرف الرسالة (Envelope)

```
Envelope {
  v            uint   // إصدار الظرف
  conv_id      uuid
  seq          uint64 // يعطيه الخادم عند القبول، متصل بلا فجوات داخل المحادثة
  sender       { account_id, device_id }
  client_msg_id uuid  // يولّده الجهاز، فريد داخل (المحادثة، المرسل)، أساس منع التكرار
  sent_at      ms     // ساعة الجهاز (للعرض فقط، لا يُعتمد عليها في الترتيب)
  received_at  ms     // ساعة الخادم عند القبول
  type         enum   // انظر الجدول
  payload      bytes  // معتم للخادم (نص صريح في المرحلة 1، شيفرة MLS في المرحلة 2)
}
```

**الخادم يرى فقط:** المحادثة، المرسل، الرقم التسلسلي، الأوقات، النوع، حجم المحتوى. لا النص ولا المفاتيح ولا محتوى الوسائط.

| `type` | يُخزَّن ويأخذ `seq`؟ | داخل `payload` |
|---|---|---|
| `text` | نعم | النص، `reply_to` (seq)، إشارات @، معاينة الرابط |
| `media` | نعم | مرجع الملف، مفتاح فك التشفير، الأبعاد، blurhash، المدة، التعليق |
| `voice` | نعم | مرجع الملف، المدة، شكل الموجة، النص المفرَّغ (اختياري) |
| `control` | نعم | `edit` أو `delete` أو `reaction` (مع `target_seq`) |
| `system` | نعم، يولّده الخادم | انضمام، مغادرة، تغيير دور، تفعيل وضع الدائرة |
| `receipt` | **لا** (حدث) | `delivered` أو `read` حتى `seq` معيّن |
| `typing`, `presence` | **لا** (حدث) | — |

> **لماذا التعديل والحذف والتفاعل رسائل `control` تأخذ `seq`؟** لأن أي جهاز رجع من انقطاع لازم يرى الحدث نفسه بالترتيب نفسه، وإلا اختلفت الأجهزة عن بعضها. ما يأخذ رقماً يُزامَن، وما لا يأخذه (يكتب…) يضيع بلا ضرر.

## 4. حالات الرسالة عند المرسل

```
pending ──► sent ──► delivered ──► read
   │          
   └──► failed (دائم) ──► [المستخدم يعيد المحاولة] ──► pending
```

| الحالة | معناها | من ينقلها |
|---|---|---|
| `pending` | محفوظة في طابور الإرسال المحلي، لم يقبلها الخادم | الجهاز عند الكتابة |
| `sent` | قبلها الخادم وأعطاها `seq` | رد `Ack` من الخادم |
| `delivered` | وصلت إلى جهاز مستلم | إيصال `delivered` من المستلم |
| `read` | فُتحت عند المستلم | إيصال `read` (مرتبط بإعداد الخصوصية عنده) |
| `failed` | رفضها الخادم رفضاً لا يُصلحه التكرار (غير مسموح، ضخمة) | رد `Error` غير قابل للإعادة |

**في المجموعات:** `delivered` و`read` عدّادان (كم عضواً)، وتُعرض العلامة الكاملة حين يبلغ العدد كل الأعضاء الحاليين. وتفاصيل «من قرأ ومتى» تُعرض عند الطلب.

**تغيير الحالة لا ينقص أبداً** (لا رجوع من `read` إلى `delivered`)، والإيصال يغطي كل ما قبله (`read` حتى `seq=120` يعني الكل حتى 120).

## 5. الإرسال ومنع التكرار

```
الجهاز                                      الخادم
  │  1) يحفظ في الطابور المحلي (pending)     │
  │  2) Send { conv_id, client_msg_id, … } ─►│  إن وُجد (conv، المرسل، client_msg_id): 
  │                                          │     يعيد الـ seq نفسه (لا تكرار)
  │                                          │  وإلا: يعطي seq التالي (ذرّياً) ويحفظ
  │◄── Ack { client_msg_id, seq, received_at}│
  │  3) يحدّث الحالة إلى sent                │──► يبثّ Event(message) للأعضاء الآخرين
```

**الثابتات (تصير اختبارات خصائص):**
- **I1:** لا يوجد رقمان تسلسليان متساويان في محادثة واحدة.
- **I2:** الأرقام التسلسلية في المحادثة متصلة (بلا فجوات) من 1 إلى آخر رقم.
- **I3:** لأي `(conv, sender, client_msg_id)` رسالة واحدة على الأكثر، مهما تكررت المحاولات.
- **I4:** ما أعاد الخادم له `Ack` لا يضيع (محفوظ قبل الرد).
- **I5:** ترتيب العرض عند كل الأجهزة = ترتيب `seq`.

## 6. المزامنة

كل جهاز يحتفظ لكل محادثة بـ`last_seq` (آخر رقم تلقّاه متصلاً).

1. عند الاتصال يرسل `Sync { conv_id → last_seq … }`.
2. يرد الخادم بكل ما بعد `last_seq` لكل محادثة (مقسَّماً إلى دفعات إن كثر).
3. **كشف الفجوة:** إن وصل `Event(message)` برقم أكبر من `last_seq + 1`، يطلب الجهاز المدى الناقص `Range { conv_id, from, to }` ولا يعرض ما بعد الفجوة قبل ملئها.
4. **تغيّرات المحادثة نفسها** (الأعضاء، الاسم، الأدوار) لها `conv_version` يُزامَن بالطريقة نفسها.
5. المحذوف يبقى **شاهداً (tombstone)** بنفس `seq` ومحتوى فارغ، فلا تنكسر الأرقام.

## 7. النقل

**WebSocket ثنائي**، والإطارات بـ Protobuf. التسجيل والملف الشخصي وجلسات رفع الوسائط والتصدير والفوترة تبقى **REST** (ليست على المسار الساخن).

| الإطار | الاتجاه | الغرض |
|---|---|---|
| `Hello` | عميل ← | الإصدار، `device_id`، القدرات، رمز الدخول (**أول إطار، لا في عنوان الاتصال**) |
| `Welcome` | ← خادم | قبول، وساعة الخادم، والحدود |
| `Send` | عميل ← | رسالة جديدة |
| `Ack` | ← خادم | قبول الرسالة مع `seq` |
| `Event` | ← خادم | رسالة جديدة، أو إيصال، أو يكتب، أو تغيّر في المحادثة |
| `Sync` / `Range` | عميل ← | طلب ما فات |
| `Receipt` | عميل ← | إيصالات مجمَّعة |
| `Ping` / `Pong` | الاثنان | بقاء الاتصال |
| `Error` | ← خادم | رمز خطأ وهل يُعاد |

**الاتصال:**
- **نبضة كل 30 ثانية**، وفقدان نبضتين يعني إعادة اتصال (لأن شبكات الجوال تقطع الاتصالات الخاملة).
- **إعادة الاتصال متدرجة:** 0.5 ثانية ثم الضعف حتى 30 ثانية مع عشوائية. وفور عودة التطبيق إلى الواجهة أو عودة الشبكة يُتصل فوراً.
- **الرمز:** رمز دخول قصير العمر (15 دقيقة) مع رمز تجديد. انتهاء الرمز لا يقطع المحادثة، بل يجدَّد في الخلفية.
- الإيصالات والكتابة **تُجمَّع** (كل 500 ملّي ثانية) ولا تُرسل واحداً واحداً.

## 8. حالات الفشل وسلوكها

| الحالة | السلوك |
|---|---|
| لا شبكة عند الكتابة | تُحفظ `pending` وتُرسل عند العودة، وتنجو من إغلاق التطبيق |
| لا `Ack` خلال 10 ثوانٍ | إعادة الإرسال بالـ`client_msg_id` نفسه بتدرّج |
| الخادم حفظ ثم سقط قبل `Ack` | إعادة الإرسال تُرجع الـ`seq` نفسه (I3) |
| انقطاع في منتصف مزامنة | تُستأنف من آخر `last_seq` محفوظ |
| وصول رسالة بفجوة | `Range` ثم العرض بالترتيب |
| رفض غير قابل للإصلاح (محتوى ضخم، غير مصرَّح) | `failed` مع سبب واضح للمستخدم |
| بطء الشبكة | لا مهلة تقطع رفع ملف جارٍ، والرفع يُستأنف |
| إعادة تشغيل الجهاز | الطابور والقاعدة المحلية تبقى، والمزامنة تكمل |
| ساعة الجهاز خاطئة | لا أثر على الترتيب (`seq`)، والعرض يستعمل `received_at` عند التعارض الكبير |

## 9. الدفع (الإشعارات)

حين لا يكون الجهاز متصلاً بالـWebSocket يرسل الخادم إشعار دفع عبر APNs/FCM:
- **الحمولة الدنيا:** `conv_id` و`seq` فقط، **بلا نص** (يتحقق مع التشفير).
- **آيفون:** امتداد خدمة الإشعار (Notification Service Extension) يجلب الرسالة ويفكّ تشفيرها على الجهاز ثم يعرضها.
- **مفتاح الطيّ (collapse key)** لكل محادثة حتى لا تتراكم الإشعارات.
- **عدّاد غير المقروء** على الأيقونة يُحسب في الخادم من الإيصالات.

## 10. الوسائط

1. الجهاز **يضغط** الملف ويولّد المصغّرة وblurhash (الخادم لا يرى محتوى مشفّراً).
2. يشفّر الملف بمفتاح عشوائي AES-256-GCM.
3. `POST /media/uploads { size, sha256_cipher, mime_class }` فيرد برابط رفع موقّع **مجزّأ يُستأنف**.
4. يرفع الأجزاء مباشرة إلى المخزن، ثم يؤكد فيعطيه الخادم `blob_id`.
5. رسالة `media` فيها (داخل `payload`): `blob_id`، المفتاح، `iv`، `sha256`، الحجم، الأبعاد، blurhash، المدة.
6. المستلم يرى blurhash فوراً، ثم يجلب الأحجام عبر CDN برابط موقّع.
7. **الحصة:** وسائط المحادثة مؤقتة ولا تُحسب، والمؤرشف الدائم يُحسب (كما في التصميم الحالي).

## 11. التعديل والحذف والتفاعل

- **حذف لدي:** محلي، ويُسجَّل في الخادم ليتزامن بين أجهزتي فقط.
- **حذف للجميع:** رسالة `control{delete,target_seq}`. المرسل ضمن المهلة (نحو يومين ونصف) أو مشرف الدائرة دائماً. النتيجة شاهد (tombstone) ومحو للمحتوى والملف.
- **تعديل:** `control{edit,target_seq,new_payload}` خلال 15 دقيقة، ويظهر «عُدّلت».
- **تفاعل:** `control{reaction,target_seq,emoji|null}`، تفاعل واحد لكل عضو على الرسالة.
- **قاعدة ذكرى:** حذف رسالة للجميع **يحذف معها** ما وُثّق منها في الأرشيف (مطبَّق اليوم في النموذج الأولي).

## 12. الدوائر فوق البروتوكول

- `circle` = `group` + قدرات: `agent_active` و`agent_from_seq` (**لا تحليل لما قبله، أي لا أثر رجعي**).
- الوكيل **عضو ظاهر بجهاز ومفتاح خاصين**، ويستلم الرسائل كأي عضو. كل الأعضاء يرون أنه عضو وأن وضع الدائرة مفعَّل.
- عناصر الأرشيف **بيانات مشتقة** يكتبها الوكيل أو المستخدم وتُزامَن كرسائل `control` من نوع `archive`. **(سؤال مفتوح: انظر القسم 15.)**
- الخلافات: لا يُكتب شيء في المحادثة (يبقى الأرشيف فقط).

## 13. الأخطاء

| الرمز | المعنى | يُعاد؟ |
|---|---|---|
| `unauthorized` | رمز غير صالح أو منتهٍ | بعد التجديد |
| `forbidden` | غير مسموح (دور) | لا |
| `not_found` | محادثة أو رسالة غير موجودة | لا |
| `rate_limited` | تجاوز الحد | نعم، بعد `retry_after` |
| `too_large` | المحتوى أكبر من الحد | لا |
| `conflict` | تعارض (مثل `client_msg_id` بمحتوى مختلف) | لا |
| `unavailable` | الخادم مشغول | نعم، بتدرّج |
| `version_unsupported` | إصدار قديم | لا (يلزم تحديث التطبيق) |
| `archive_readonly` | الأرشيف مجمَّد (الاشتراك) | لا |
| `quota_exceeded` | تجاوز الحصة | لا |

| الحد | القيمة المبدئية |
|---|---|
| حجم نص الرسالة | 64 كيلوبايت |

## 15. أسئلة مفتوحة (تُحسم في المرحلة 1 و2)

1. **Protobuf أم CBOR** للإطارات؟ (أميل إلى Protobuf لنضج الأدوات.)
2. **مكتبة MLS:** OpenMLS أم غيرها؟ وتقييم النضج على الجوال.
3. **توزيع الرسالة في المجموعات الكبيرة** (fan-out) وقناة التوزيع بين البوابات.
4. **تزامن السجل بين الأجهزة المتعددة** (جهاز جديد يريد التاريخ).
5. **الوكيل تحت التشفير:** كيف يكتب عناصر الأرشيف ويحافظ على سرية الباقي؟ وهل تُشفَّر عناصر الأرشيف نفسها؟
6. **البحث تحت التشفير:** فهرس محلي على الجهاز، وماذا عن جهاز جديد؟
7. **ساعة الخادم والجهاز:** كم نثق بـ`sent_at` للعرض؟

## 16. من النموذج الحالي إلى البروتوكول

| اليوم (REST) | البروتوكول |
|---|---|
| `POST /circles/:id/messages` | `Send` على WebSocket |
| استطلاع `GET …/messages?after=` | `Event` يُدفع + `Sync` عند الاتصال |
| استطلاع `GET …/deletions?since=` | رسائل `control{delete}` بالـ`seq` |
| `POST /messages/:id/hide` | حذف لدي (مسجَّل ومتزامن بين أجهزتي) |
| `DELETE /messages/:id` | `control{delete}` |
| تسجيل الدخول، الملف الشخصي، الفوترة، الاستيراد، التصدير | تبقى REST |
| `POST /circles/:id/voice` (رفع عبر الخادم) | رفع مجزّأ إلى المخزن (القسم 10) |

## 17. الاختبار

- **عقود:** إطارات «ذهبية» مخزّنة يُتحقق منها من الطرفين.
- **خصائص (Property tests):** الثوابت I1 إلى I5 تحت إسقاط وإعادة ترتيب وتكرار عشوائي للإطارات، وانقطاع عشوائي، وسقوط الخادم في كل نقطة.
- **شبكة سيئة:** محاكاة فقد حزم وتأخير (3G).
- **القبول:** أهداف القسم 6 من [الخطة الشاملة](MASTER-PLAN.md#6-أهداف-الجودة-القابلة-للقياس) على جهاز القياس نفسه. **الهدف الأول: أن يهبط p95 للوصول من 2.9 ثانية إلى أقل من 300 ملّي ثانية.**
