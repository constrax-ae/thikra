# جهاز قياس الأداء

يقيس ما إذا كانت الرسالة تصل بسرعة واتساب، مقابل أهداف [الخطة الشاملة §6](../docs/MASTER-PLAN.md#6-أهداف-الجودة-القابلة-للقياس).

```bash
pnpm bench                          # يشغّل خادماً هنا ويقيس التصميم الحالي (استطلاع كل 3 ثوانٍ)
pnpm bench --poll-ms 1000           # لو استطلع العميل أسرع
pnpm bench --base-url http://host   # قياس خادم يعمل
```

## ما يقيسه وما لا يقيسه
- **يقيس:** كلفة الكتابة في الخادم، وزمن وصول الرسالة للمستلم كما يعمل العميل (يسأل كل فترة)، وكلفة الخمول.
- **لا يقيس الشبكة:** يعمل على الجهاز نفسه (loopback)، فأي شبكة حقيقية **تزيد** هذه الأرقام. ويعزل التصميم عن الشبكة، وهذا هو المقصود.

## الأساس المسجَّل (التصميم الحالي)
انظر `bench/results/`. أول قياس (استطلاع كل 3 ثوانٍ، 8 مستلمين):

| المقياس | القيمة | الهدف |
|---|---|---|
| كتابة رسالة، p95 | 4.2 ملّي ثانية | أقل من 50 ✅ |
| **وصول الرسالة للمستلم، p95** | **2883 ملّي ثانية** | **أقل من 300 ❌** |
| كلفة الخمول | 667 طلباً/ثانية لكل 1000 عميل متصل، وهم لا يفعلون شيئاً | — |

**القراءة:** الخادم سريع، والتصميم هو العقبة: الرسالة تنتظر أن يسأل المستلم. العلاج هو الاتصال الدائم ([البروتوكول](../docs/PROTOCOL.md)). وعند بنائه نضيف استراتيجية `websocket` هنا ونقارن على الجهاز نفسه.

**تحفّظ صريح:** loopback بلا شبكة حقيقية، وJSON لا Protobuf، وخادم واحد. الرقم يثبت أن العقبة كانت التصميم لا الخادم؛ ولا يثبت بعد الأداء على شبكة جوال ضعيفة (F-07) ولا عند آلاف المتصلين.
